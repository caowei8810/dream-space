# 部署与发布方案

本文档区分当前可运行环境和商用目标环境。GitHub Pages 只部署 `prototype/` 供视觉演示，不能承载正式用户端、API、Worker 或用户数据。

## 当前环境能力

| 环境       | 用途                                   | 当前实现                                             | 是否可承载真实用户 |
| ---------- | -------------------------------------- | ---------------------------------------------------- | ------------------ |
| 本机开发   | 开发、专项 smoke、人工验收             | macOS 物理机上的 PostgreSQL、Redis、MinIO 和四个应用 | 否                 |
| PR CI      | 静态检查、测试、构建、迁移、smoke、E2E | GitHub Actions 临时 PostgreSQL/Redis                 | 否                 |
| 原型 Pages | 展示 `prototype/` 视觉与交互基线       | 合并 `main` 后静态部署                               | 否                 |
| 预发布     | 生产同构验证、真实供应商沙箱、发布演练 | 尚未建设                                             | 否                 |
| 生产       | 首批商用用户                           | 尚未建设                                             | 是，D1-D6 通过后   |

## 本机物理机启动

首次安装依赖：

```bash
brew install postgresql@17 redis minio minio-mc
pnpm install --frozen-lockfile
```

启动、查看状态、日志、重启和停止：

```bash
pnpm local:up
pnpm local:status
pnpm local:logs
pnpm local:restart
pnpm local:down
```

`local:up` 会启动本地基础设施，执行 Prisma Client 生成、迁移和演示数据种子，再启动 API、Worker、用户端和管理端。PID、日志、本地对象和随机 MinIO 凭据只保存在被 Git 忽略的 `.local/`。

访问地址：

- 用户端：`http://localhost:3000`
- 管理端：`http://localhost:3001`
- API 健康检查：`http://localhost:4000/health`

本机脚本是开发便利工具，不提供进程高可用、TLS、自动备份、集中日志或生产密钥管理。

## 商用目标拓扑

首次商用建议保持应用架构简单，但基础设施必须托管和隔离：

```text
Internet
  -> DNS / CDN / WAF / TLS
  -> Web 与 Admin
  -> API（至少两个实例）
       -> 托管 PostgreSQL（高可用、PITR）
       -> 托管 Redis（队列与短期协调）
       -> S3 兼容对象存储（私有 bucket）
  -> Worker（独立扩缩容，至少两个实例）
       -> 模型与内容审核供应商
       -> 对象存储

日志、指标、追踪 -> 集中可观测平台 -> 告警和值班
密钥 -> 云密钥管理服务 -> 运行时注入
```

不建议在首发阶段为了形式引入微服务或 Kubernetes。API 与 Worker 分进程已经能独立扩缩容；托管数据库、队列、对象存储、可观测性和可靠发布比编排平台复杂度更优先。最终云平台选型必须满足数据地域、备份、审计、成本和供应商网络要求。

## 环境隔离

- `development`、`test`、`staging` 和 `production` 使用独立数据库、Redis、bucket、域名、管理员和供应商凭据。
- 生产数据不得复制到开发或 CI；必须排障时使用脱敏后的最小数据集。
- `EXTERNAL_SERVICES_MODE=mock` 只允许本地和 CI。预发布按用例显式选择，生产必须为 `live` 并在启动时验证真实适配器。
- 生产对象存储必须为 `s3`，禁止失败后回退本地目录。
- 所有 Secret 由部署平台或密钥管理服务注入，不进入镜像、仓库、构建日志和前端变量。

## 生产配置门禁

正式发布前至少验证：

- `NODE_ENV=production`，公开 URL 和 Web/Admin Origin 使用 HTTPS 精确域名。
- PostgreSQL 强制 TLS、最小权限和连接池；迁移账户与应用账户分离。
- Redis 使用 TLS、认证和网络隔离，禁止公网直连。
- 对象 bucket 私有，生命周期、版本保护、跨域和签名 TTL 经审查。
- Cookie 使用 `Secure`、`HttpOnly` 和适当的 `SameSite`；可信代理、CORS 和 CSRF 策略与反向代理一致。
- API 限流、上传上限、供应商超时、任务重试、队列并发和成本上限有显式值。
- 对账调度具备多实例租约和崩溃接管，不只依赖单窗口唯一键。

当前代码尚未满足全部门禁，具体阻断项见 [商用就绪审计](commercial-readiness.md)。

## 构建与发布流程

1. 功能分支完成本地检查和用户验收后，提交 PR。
2. PR CI 执行格式、lint、类型、单元测试、生产构建、迁移、smoke 和 E2E。
3. 合并后构建一次不可变、可追溯的产物，记录提交 SHA、依赖锁和迁移版本；预发布与生产使用同一产物。
4. 部署预发布，执行真实存储、供应商沙箱、权限、审核、额度和故障恢复 smoke。
5. 生产发布前备份并检查迁移。数据库变更使用 expand-contract：先增加兼容结构，再部署应用，最后在后续版本清理旧结构。
6. 先部署 API/Worker 小比例实例，等待健康、错误率、队列和额度指标稳定，再逐步放量 Web/Admin。
7. 达到错误率、延迟、任务失败、额度差异或供应商成本停止阈值时自动终止放量。
8. 发布完成后执行只读业务 smoke，并记录发布人、产物、迁移、指标和结论。

未经用户明确批准，不合并 PR。任何环境不得使用聊天中出现过或已泄漏的访问令牌。

## 健康与就绪

现有 `/health` 只能证明 API 进程可响应。生产前需区分：

- 存活探针：进程事件循环可响应，不因下游短暂故障反复重启。
- 就绪探针：数据库连接、关键配置和必要依赖可用，未就绪实例不接收流量。
- Worker 就绪：Redis、PostgreSQL、对象存储和 live 适配器配置有效。
- 业务 smoke：登录、公开灵感、提交任务、SSE、结果访问、管理查询和额度对账按最小只读或探针账户验证。

探针账户和对象必须隔离、限额、可追踪并自动清理，不得污染真实用户或账务。

## 回滚策略

应用代码优先回滚到上一个不可变产物；数据库不得直接向下执行破坏性迁移。

1. 停止放量并隔离故障版本。
2. 若迁移仍与旧应用兼容，回滚 API、Worker、Web 和 Admin 到上一产物。
3. 若数据库已发生不可逆变化，执行预先准备的前向修复，不临场删除列或恢复整库覆盖新数据。
4. 暂停高风险写操作或生成队列时，要保留已接受任务和额度状态，恢复后通过幂等处理与对账收敛。
5. 发布事故结束后核对任务、额度流水和对象引用，并形成事件复盘。

原型 Pages 的回滚仍通过 PR 回滚 `main` 的相关提交，禁止强推或直接修改部署产物。

## 备份与恢复

建议的首发内部目标为 RPO 不高于 15 分钟、RTO 不高于 4 小时；它们必须在 D4 根据业务损失、平台能力和演练结果正式批准，不能直接作为对外 SLA。

- PostgreSQL：自动快照、连续归档/PITR、跨故障域副本和定期恢复验证。
- 对象存储：版本保护或等价防误删能力、生命周期策略、服务端加密和引用一致性清单。
- Redis：不作为唯一业务事实；恢复后从 PostgreSQL 识别未完成任务并按规则重投或人工处置。
- 配置与密钥：备份恢复流程只保存加密引用，不在普通备份中明文导出 Secret。

每次恢复演练必须验证账户、额度流水、任务、结果元数据和对象字节一致，并记录实际 RPO、RTO 和未恢复项。

仓库提供 `scripts/backup-restore.sh` 作为可审计的演练工具：

```text
backup-restore.sh backup /absolute/empty/backup-dir
backup-restore.sh verify /absolute/backup-dir
backup-restore.sh restore /absolute/backup-dir --confirm
```

工具使用 `pg_dump` 自定义格式保存数据库，复制配置的对象存储并生成 SHA-256 清单，同时从数据库导出未删除参考图和生成结果对象引用。校验会拒绝缺失对象或不安全对象键；恢复要求显式 `--confirm`，本地对象恢复目标必须为空。生产环境仍应由托管数据库快照/PITR、对象版本保护和密钥管理服务提供实际备份介质，脚本用于预发布隔离演练和恢复证据留存。

## 原型 GitHub Pages

`.github/workflows/deploy-pages.yml` 仅将 `prototype/` 部署为静态设计参考。首次启用时在仓库 `Settings > Pages` 中选择 GitHub Actions；合并到 `main` 后由工作流发布。它没有正式 API、鉴权、数据库、私有对象或内容审核能力，不能作为商用部署方案。
