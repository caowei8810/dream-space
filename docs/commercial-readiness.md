### 本次关键纠偏

额度对账最初尝试用仍存在的成功任务推导历史消费，这会在用户删除会话或任务后产生伪差异。现已明确额度流水是账务事实来源：

```text
total     = SUM(GRANT)
available = GRANT - RESERVE + RELEASE
reserved  = RESERVE - CONSUME - RELEASE
```

任务表仅用于发现某个任务缺失的 `RESERVE`、`CONSUME` 或 `RELEASE`，以及判断退款是否能被安全证明。金额不一致、余额漂移或无法证明归属的预留只记录为 `BLOCKED`，禁止自动猜测修复。这一模型能容忍业务数据按规则删除，同时保留不可变账务证据，符合商用额度系统的审计要求。

## 已确认的架构决策

### 2026-08-14 管理端基线复核

本次复核确认：对账交互从管理端近期主路径降为 P2，但额度流水、幂等补偿和 `BLOCKED` 人工处置仍是 P0 安全约束；管理端下一主线为 ADM-0 至 ADM-4。现有代码只覆盖管理员登录、基础 RBAC、任务查询、灵感管理和对账摘要，不能称为完整商用后台。

新增的管理端基线明确了 Identity、Content、Moderation、Generation Ops、Model Ops、Operations 和 Quota/Accounting 的数据归属，并要求高风险动作执行审批人分离、原因必填、状态迁移校验和不可抵赖审计。后续每个切片必须经过“实现 -> 自测 -> 用户验收 -> PR”门禁，未验收不得提交。

该复核没有改变用户端 1:1 原型复刻范围，也没有提前假设具体模型供应商、审核供应商或收费方案；外部协议确定前只实现供应商无关的适配器边界。

| 编号    | 决策                                                               | 理由                                                                     | 复审触发条件                               |
| ------- | ------------------------------------------------------------------ | ------------------------------------------------------------------------ | ------------------------------------------ |
| ADR-001 | 保持模块化单仓库，API 与 Worker 分进程，不提前拆微服务             | 当前团队和流量尚不需要分布式复杂度；共享契约、事务和测试更重要           | 单模块需要独立扩缩容、发布节奏或故障隔离时 |
| ADR-002 | PostgreSQL 是业务与额度账务真相来源，Redis 只承载可恢复队列        | 避免队列状态变成不可审计业务事实；Redis 丢失后可从数据库识别和补偿       | 引入事件总线或跨区域主动主动架构时         |
| ADR-003 | 外围服务统一支持 `mock/live`，生产环境禁止静默回退 mock            | 本地和 CI 可重复，生产配置错误必须快速失败，避免伪成功                   | 每个真实适配器上线时增加启动探针和合约测试 |
| ADR-004 | 供应商未确定前只实现稳定适配器边界                                 | 避免虚构请求字段、错误码和回调语义造成返工                               | 确定供应商、沙箱凭据、限额和 SLA 后        |
| ADR-005 | 对账只自动修复可证明且幂等的差异                                   | 错误补偿比延迟人工处理风险更高；不确定项必须进入运营处置                 | 引入人工审批、双人复核和完整审计后         |
| ADR-006 | 本机不依赖 Docker；生产环境仍使用托管 PostgreSQL、Redis 和对象存储 | 开发机限制不应降低生产高可用、备份和安全能力                             | 部署平台最终选型时                         |
| ADR-007 | 当前商用范围不含支付、会员和充值                                   | 现有产品、账务和合规只覆盖免费额度；收费会引入订单、退款、发票和支付合规 | 产品决定收费时单独建立商业化阶段           |

## 计划治理规则

1. 每个子阶段必须具备目标、非目标、准入条件、验收证据和退出条件。
2. 阶段实现完成后先自测；自测通过后通知用户验收；用户验收通过后才提交、推送并创建 PR。
3. 外部依赖阻塞时，只能并行推进依赖无关且不会锁死协议的工作，并在计划中记录理由。
4. 影响数据真相、资金或额度、安全边界、用户隐私、供应商锁定和生产拓扑的决策必须记录在本文件。
5. 任何生产事故无法通过现有日志和指标解释，视为可观测性缺陷进入后续阶段，不能只做人工补数据。
6. 每次阶段评估同时核对代码、迁移、运行环境、文档和回滚路径，避免文档状态滞后。

## 首次商用上线判定

首次商用上线至少需要同时满足：C3b、C4b、C5、D1-D6 全部完成；P0 风险全部关闭；P1 风险有明确负责人和经批准的处置期限；预发布环境完成一次全链路生成、故障、对账、恢复和回滚演练。支付和会员不属于这次上线判定。
